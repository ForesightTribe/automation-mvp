1. get_page — coordinate -> store   (discovery only)
==============================================================================
GET https://bff-gateway.zepto.com/lms/api/v2/get_page
      ?latitude=<lat>&longitude=<lon>&page_type=HOME&version=v2
      &show_new_eta_banner=true&page_size=3&enforce_platform_type=WEB

RESPONSE (trimmed)
  storeServiceableResponse.storeId            the serving store
  storeServiceableResponse.secondaryStoreIds  its secondaries
  storeDetailsResponse.name / .city           human labels

NOT on the scrape path. The catalog already holds every store id, and this
endpoint carries its own separate rate-limit budget — calling it per store
drains that budget for nothing.

2. search — keyword at a store   (the public data)
==============================================================================
POST https://bff-gateway.zepto.com/user-search-service/api/v3/search

BINDING — the single most important fact about this platform.
A search binds to a store by HEADER, never by coordinate. lat/lon in the body is
accepted and SILENTLY IGNORED: you get a valid 200 carrying a generic catalog.

  store_id    <uuid>          store_ids   <primary>,<secondary>,...
  storeid     <uuid>          store_etas  {"<id>": -1, ...}

Every other header is captured from a live browser session and replayed; they
are session/device values that go stale, which is why they are captured rather
than hardcoded.

REQUEST BODY
  {"query": "sourdough", "pageNumber": 0, "mode": "SHOW_ALL_RESULTS",
   "userSessionId": "<from the browser's own request>"}

RESPONSE ENVELOPE
  layout[]                                  null past the end of results —
    widgetId == "PRODUCT_GRID"              NOT [], so `.get("layout") or []`
      data.resolver.data.items[]            the products
    widgetId == "HEADER_WIDGET"             SECTION BREAK — stop collecting.
                                            What follows is a "Similar Products"
                                            carousel, not ranks.

3. Status codes — three mechanisms, three remedies
==============================================================================
  200   ok
  429   too fast, right now      connection-wide   clears ~60-80s   slow down
  299   LOGIN_REQUIRED           connection-wide   clears ~60s      pause, retry
        body: {"error_code": "LOGIN_REQUIRED",
                "message": "Oops! Please login to continue searching"}
  202   AWS WAF challenge        per session       NEVER clears     re-mint pass
        header: x-amzn-waf-action: challenge

A 299 or 429 is NEVER an empty shelf. Recording either as zero products invents
a plausible, well-formed, wrong answer.
